# Pure-helper runtime prewarm (2026-09-10)

## Question

The accepted opt-in pure-helper lane uses seven state-free tensor-helper
families, which instantiate as eight Inductor graphs because scaled residual
has BF16 and FP32 contracts.  The helpers were previously compiled lazily by
the first real model invocation.  This experiment tests whether the exact
helper instances installed on the live 30-block model can be invoked with
shape-matched synthetic tensors before the runtime is declared ready.

The starting repository commit was `91467f7d77ac5373f1763155f1c22082fbaa844f`.
The unrelated edit to `scripts/run_window_sweep.sh` was left untouched and
unstaged.

## Prewarm contract

`prewarm_pure_tensor_islands()` receives the `PureTensorIslands` instance
returned by the real `install_on_blocks()` call.  It does not create a
temporary helper bank and does not pass tensors through model blocks.  It
invokes these exact live callable objects:

| Helper family | Contract |
| --- | --- |
| modulation | parameter `[1, 6, 1536]` BF16 plus `[1, 1008, 6, 1536]` FP32 conditioning |
| affine | `[1, 1008, 1536]` FP32 activation and live singleton-dimension view strides |
| scaled residual | BF16 and FP32 activation variants, BF16 residual |
| add | FP32 activation plus BF16 residual |
| SiLU | `[1, 1008, 1536]` BF16 |
| tanh-approximate GELU | `[1, 1008, 8960]` BF16 |
| camera update | FP32 activation with BF16 camera tensors |

The synthetic tensors are zero-filled.  The modulation input is a
non-gradient `Parameter`, and the modulation outputs use the same
`.squeeze(2)` views as the live block.  This preserves the live type/stride
guards and avoids creating extra graphs.  No generation RNG is consumed:
CPU and GPU RNG states were equal before and after prewarm.  No KV, decoder,
camera, prompt, or session state is passed to the helper bank.

## Startup lanes

Times are milliseconds from process start.  `Runtime ready` is the explicit
boundary after model/session preparation, TAE construction, and (for the
candidate lanes) prewarm, but before automatic bootstrap generation.

| Boundary | Cold lazy | Cold explicit prewarm | Populated-cache prewarm |
| --- | ---: | ---: | ---: |
| process → Runtime ready | 179245.7 | 179969.2 | 60911.1 |
| explicit prewarm | 0 | 4315.1 | 1777.7 |
| Runtime ready → bootstrap transformer end | 7553.1 | 754.0 | 754.3 |
| Runtime ready → bootstrap first RGB | 7686.9 | 895.0 | 903.6 |
| first action → first RGB | 617.3 | 643.4 | 661.6 |

The cold explicit lane intentionally moves about 4.3 seconds into the
pre-READY phase; it does not reduce total process-to-ready time in this
machine run.  It removes the unexpected multi-second first bootstrap stall.
The populated compiler cache reduces explicit prewarm to about 1.78 seconds,
but does not make runtime prewarm free.  Its counters show eight FX graph
cache hits and cached AOT/autotuner activity, while runtime async/static
compilation activity remains.  Therefore disk cache population is useful but
is not a substitute for an explicit prewarm call.

## Coverage and compiler behavior

Both 40-action lanes instantiated exactly eight graphs from 23 captured
helper calls.  Neither lane logged graph breaks or recompilations.  The
prewarm lane's post-READY generation did not create additional helper graphs.
The compiler diagnostics contained no `aten.addmm`, `aten.mm`, or `aten.bmm`.
The 16 validator-matched TunableOp results remained loaded with online tuning
and untuned recording disabled; all Linear/GEMM, SDPA, KV/cache, rollover,
TAEHV, and clean-KV behavior remained outside the compiled helpers.

## Steady-state A/B

The authoritative comparison is the rolled portion of matched 40-action
sessions.  The cold lazy control had 29 rolled actions; the cold-prewarm
candidate also had 29.

| Rolled metric | Cold lazy | Cold prewarm | Delta (prewarm - control) |
| --- | ---: | ---: | ---: |
| 3× denoise median | 914.9 ms | 922.6 ms | +7.7 ms |
| 3× denoise p95 | 922.9 ms | 931.9 ms | +9.0 ms |
| first-visible median | 935.3 ms | 943.2 ms | +7.9 ms |
| first-visible p95 | 943.4 ms | 952.5 ms | +9.1 ms |
| clean KV median | 299.5 ms | 301.9 ms | +2.4 ms |
| next-ready median | 1284.5 ms | 1292.4 ms | +7.9 ms |
| next-ready p95 | 1291.3 ms | 1302.1 ms | +10.8 ms |

The small candidate slowdown is within the observed run-to-run spread and is
not a repeatable regression established by this one pair.  The intended
benefit is startup predictability, not warmed inference speed.

## Correctness

The cold-prewarm 40-action session remained finite and ended at:

```text
global KV position: 41328 tokens
local capacity:     12096 tokens
sink retained:       6048 tokens
```

It crossed repeated rollovers with the accepted one-slot input policy and
exact clean `t=0` transaction intact.  A fresh populated-cache 14-frame
transfer reached the expected `14112` local-token capacity with `6048` sink
tokens and remained finite; it used the same eight helper graphs without a
second tuning campaign.  Prewarm preserved CPU/GPU RNG state.  This test did
not add a latent-hash comparison, so it does not claim bitwise output
identity across fresh processes; it establishes state and finiteness
equivalence for the startup change.

## Decision

**RETAIN AS OPT-IN RELEASE PREPARATION.** The explicit prewarm path warms the
actual live helper instances before `Runtime ready`, preserves TunableOp and
the accepted stateful path, and removes the multi-second first-bootstrap
compile surprise.  Keep the accepted non-prewarmed path as the default until
the startup UX and machine-specific compiler-cache packaging are finalized.
