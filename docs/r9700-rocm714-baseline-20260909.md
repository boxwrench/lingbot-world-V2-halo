# R9700 ROCm 7.14 LingBot 1.3B baseline — 2026-09-09

This is the requested newer-stack control run from the Strix Halo study. It
was executed on the R9700 / gfx1201, not on the Strix host. The old ROCm 7.2.1
result and its temporal-split workaround remain separate historical evidence.

## Runtime

```text
GPU:      AMD Radeon AI PRO R9700 / gfx1201
PyTorch:  2.12.0+rocm7.14.0
HIP:      7.14.60850
MIOpen:   3.5.2.cd957402
dtype:    native BF16 transformer; FP32 VAE weights/output
attention: torch.nn.functional.scaled_dot_product_attention
```

The model was the pinned `lingbot-world-v2-1.3b-causal-fast` six-shard
checkpoint. The temporary runtime layout supplied the shared VAE, T5, and
tokenizer assets. A temporary `use_safetensors=True` argument was needed for
the ROCm 7.14 environment's Diffusers loader. The run used
`MIOPEN_FIND_MODE=FAST`, an isolated user FindDb, and
`WAN_VAE_CONV3D_TEMPORAL_SPLIT=0`.

## Capacity boundary

The first no-offload smoke attempt failed during VAE encode: MIOpen requested
approximately 14.91 GiB while the transformer was resident. The reported
state was about 18.38 GiB allocated and 11.80 GiB free on a 31.86 GiB device.
This failure is preserved under
`results/raw/lingbot/r9700-rocm714-smoke-failure/` locally.

For the successful control, the existing experiment-only offload flag was
extended locally to move the transformer to CPU before VAE encode and restore
it before DiT inference. `PYTORCH_NO_CUDA_MEMORY_CACHING=1` was required to
avoid allocator fragmentation around the large VAE workspace. This is a
R9700 capacity workaround, not part of the upstream PR and not a Strix
recommendation.

## Baseline command

```bash
unset LD_LIBRARY_PATH CUDA_VISIBLE_DEVICES
export HIP_VISIBLE_DEVICES=1
export WAN_VAE_CONV3D_TEMPORAL_SPLIT=0
export MIOPEN_FIND_MODE=FAST
export MIOPEN_USER_DB_PATH=/tmp/r9700-rocm714-vae
export PYTORCH_NO_CUDA_MEMORY_CACHING=1

python scripts/run_experiment.py \
  --size 480*832 --frames 81 --chunk-size 4 \
  --local-attn-size 18 --sink-size 6 --seed 42 \
  --repeat 2 --offload-model true
```

The exact remote invocation and prompt/image/action paths are retained in the
raw JSON's `arguments` field. The source was the pinned R9700 bring-up branch
with metrics-only instrumentation plus the runtime capacity handling above.

## Result

The implementation normalizes the requested 81 frames to 77 frames: 20
latent frames, five causal chunks of four latent frames each, and the final
`(20 - 1) * 4 + 1` video-frame count.

| Measurement | Cold run | Warm run |
|---|---:|---:|
| Model initialization | 31.390 s | same process |
| T5 encode | 3.702 s | cache hit |
| VAE encode | 50.981 s | 49.695 s |
| DiT, five chunks | 27.198 s | 27.129 s |
| VAE decode | 83.095 s | 82.782 s |
| Total generation | **167.341 s** | **160.674 s** |
| Effective FPS | 2.773 | 2.888 |
| Median chunk | 5.192 s | 5.331 s |
| Mean chunk | 5.440 s | 5.426 s |

The output tensor was `[77,464,832]`, finite, in `[-1,1]`. The second run
matched the first exactly (`max_abs_diff=0.0`, `mean_abs_diff=0.0`) for this
seed and configuration. The saved MP4 is padded by the default imageio-ffmpeg
macroblock handling to 80 encoded rows; the raw generated tensor remains
464×832.

## Memory and placement

The transformer parameter report counted 1,709,502,016 BF16 parameters and
placed them on `cuda:0` (the visible R9700). T5 parameters were CPU-resident;
the VAE was GPU-resident during VAE work. With the experiment-only offload
boundary, the process's post-generation PyTorch allocation was zero because
the model/VAE were released before the final snapshot. Therefore that field
is not a peak measurement. A live ROCm SMI snapshot during the baseline saw
the process using approximately 13.75 GB of device memory. Peak process RSS
was 25.71 GB; final `/proc/meminfo` showed 134.13 GB available system RAM.

The isolated VAE control reached 21.24 GiB peak PyTorch allocation and
27.15 GiB reserved. These numbers explain why keeping the transformer
resident is not viable on this 32 GiB R9700 under the observed MIOpen
workspace behavior.

## Interpretation

The newer R9700 stack runs the complete 1.3B causal-fast path correctly in
BF16/SDPA, and the Conv3d cliff is gone. However, on this 32 GiB card the
large VAE workspace and transformer cannot safely coexist with the other
GPU users present on the host. The dominant practical costs in this control
are VAE decode and encode, not attention: decode is about 83 s and the five
DiT chunks take about 27 s.
