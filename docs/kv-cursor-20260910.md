# Host-side KV cursor experiment — 2026-09-10

## Decision

**Reject as a release optimization.** The opt-in host-cursor path is
correct and removes the model-side scalar synchronization calls, but the
fresh matched 40-action result improved rolled first-visible P50 by only
`8.256 ms` and next-action-ready P50 by `9.989 ms`. That is below the
`15–20 ms` release-candidate threshold and is consistent with ordinary run
variance. The accepted defaults remain unchanged.

The implementation and evidence are retained as an opt-in diagnostic because
the mechanism is well isolated and the correctness result is strong.

candidate was opt-in via `--host-kv-cursor`.

## Cursor contract

Each of the 30 causal self-attention layers owns tensor mirrors named
`global_end_index` and `local_end_index`. The upstream path reads those
tensors with `.item()` for rollover and slice-index calculations, then
updates the mirrors with `fill_` after attention.

The live trace found no evidence that the cursor values are device-computed:
they are deterministic counters derived from the host-controlled current
frame/chunk offsets and cache capacity. Every layer had equal cursor values at
all tested points: early startup, full capacity, first eviction, repeated
rollover, and the exact clean t=0 pass.

The candidate adds per-layer Python integers:

```text
global_end_index_py
local_end_index_py
```

These are authoritative only when the opt-in key is present. The existing
tensor cursors remain allocated and are still updated as compatibility
mirrors. No single global cursor was introduced; layer-local Python mirrors
are maintained independently.

Logical cache behavior is unchanged: at 12 frames the cache retains 6 sink
frames (`6048` tokens), 5 recent frames (`5040` tokens), and 1 current frame
(`1008` tokens), for `12096` attended tokens.

## Synchronization evidence

Static/live tracing counted `360` model-side cursor `.item()` reads per
rolled action: six reads per layer for the first/rollover denoise, two reads
per layer for each of the other two denoise passes, and two reads per layer
for clean KV. Reporting/tooling reads are separate.

A mechanism-only PyTorch profiler trace at rolled chunk 13 recorded:

| Event | Tensor cursor control | Host cursor candidate |
|---|---:|---:|
| `aten::item` calls | 401 | 41 |
| `aten::_local_scalar_dense` calls | 401 | 41 |
| `hipStreamSynchronize` calls | 389 | 29 |
| `aten::item` CPU time | 614.395 ms | 0.712 ms |
| `_local_scalar_dense` CPU time | 613.256 ms | 0.633 ms |
| `hipStreamSynchronize` CPU time | 610.802 ms | 0.371 ms |

The remaining 41 scalar reads and 29 stream synchronizations are harness or
measurement-boundary activity. The profile is intentionally intrusive and is
mechanism evidence, not a product-latency measurement.

## Correctness

The dedicated same-process equivalence harness compared independent control
and candidate cache states over 16 chunks, including fill, first rollover,
repeated rollover, and exact clean t=0 commits:

```text
all_x0_exact                 true
all_denoise_caches_equal     true
all_clean_caches_equal       true
all_host_mirrors_equal       true
all outputs finite            true
```

The final direct-harness state was `16128` global tokens with a `12096`
local capacity. The fresh 40-action live runs both reached global position
`41328`, retained `12096` local tokens and `6048` sink tokens, and produced
finite latents/RGB throughout. The clean t=0 transaction remained exact.

No 14-frame regression was run because the 12-frame candidate did not meet
the release performance gate; there was no reason to extend a rejected
optimization into a second mode.

## Release impact

Do not enable `--host-kv-cursor` in the public default. The exact host-side
representation is a useful diagnostic and may simplify future compiler or
runtime work, but this measurement does not establish a meaningful product
latency win. The next authorized experiment remains shape-matched compile
prewarm; it was not started here.
