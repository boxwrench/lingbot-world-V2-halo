# Regional `torch.compile` probe on gfx1151 — 2026-09-10

## Result

Rejected. A single leading `CausalWanAttentionBlock` was wrapped with
`torch.compile(..., backend="inductor", mode="default", fullgraph=False)` while
the validator-matched TunableOp file remained enabled. The real persistent live
runner completed its process, but the generated latent and RGB output became
non-finite immediately after the bootstrap action. The ordinary TunableOp-only
runner is finite with the same model and workload.

This is a feasibility failure, not a performance comparison. The experiment
was stopped before compiling all 30 blocks or running a long control/candidate
A/B.

## Compiler feasibility evidence

The one-block process produced:

| Counter | Result |
|---|---:|
| compiled block wrappers | 1 of 30 |
| Dynamo frames | 32 total, 32 OK |
| unique Inductor graphs | 27 |
| Dynamo graph-break events | 23 (`7` data-dependent scalar, `16` `Tensor.item`) |
| logged recompilation events | 124 lines in the diagnostic log |
| Inductor async compile cache misses | 82 |
| Inductor extern calls | 103 |

The diagnostic log repeatedly identifies the stateful cache code in
`wan/modules/model_fast.py` as the specialization boundary. Representative
guards include `local_end_index.item()`, `global_end_index.item()`,
`current_end == 1008`, and the rollover comparison at lines 133–161. The
corresponding `Tensor.item()` operations trigger graph breaks because scalar
capture is disabled. The resulting regions are not one stable block graph.

The compiler counters also show captured `aten.addmm` signatures for the
compiled block. Because there was no supported runtime record proving that
these Inductor-generated regions continued to use the persisted TunableOp
hipBLASLt selections, TunableOp preservation is **not established**. The
candidate therefore fails both the state-stability and TunableOp-preservation
gates.

## Correctness result

The candidate run reached 14 actions including bootstrap and exited with the
runner's normal success status, but that status is not a correctness pass:

| Point | Result |
|---|---|
| bootstrap chunk | finite |
| first subsequent action | `latent_finite=false`, `output_finite=false` |
| warnings | NumPy invalid-value cast during RGB conversion |
| KV capacity | remained configured at 12,096 tokens, but output state was invalid |
| persistent traversal | rejected; no long validation authorized |

The first compiled bootstrap transformer interval was `8,581.99 ms`, compared
with `779.17 ms` for the prior TunableOp-only bootstrap profile. This includes
lazy graph compilation and is not an inference number. A clean warm compiler
cache restart was not run because the candidate had already failed the
correctness gate.

The wrapper construction itself took `0.472 s`; this is only wrapper creation,
not lazy Inductor compilation.

## Interpretation

The current full `CausalWanAttentionBlock` is not a suitable direct regional
compile target on this build. Its mutable KV dictionaries, scalar cache-index
reads, rollover branches, and in-place cache updates cause graph fragmentation,
recompilation on changing state, and an invalid persistent result. No causal
semantics were changed to make `fullgraph=True` succeed.

This does not prove that all compilation is impossible. It does show that the
requested bounded full-block intervention is not safe or measurable without
first separating a pure state-free subregion from cache management and
state-sensitive attention. No such refactoring is included in this commit.

## Decision

**Reject regional compilation of the current full causal block.** The accepted
TunableOp-only path remains the product configuration. No compile candidate is
enabled by default, and no 14-frame transfer test was run.

## Next recommendation

If compilation is revisited, the one bounded follow-up should compile only a
new, explicitly state-free helper covering norm/modulation/residual/FFN work,
while leaving attention, KV reads/writes, rollover logic, and all TunableOp
linear dispatch outside the compiled region. First prove finite persistent
execution and stable graph count before measuring latency.
