# TAEHV presentation-decoder experiment

Date: 2026-09-10  
Host: Strix Halo, Radeon 8060S, `gfx1151`  
Model: LingBot World v2 1.3B causal-fast  
Mode: `384x672`, chunk size 1, 3 denoise points, world window `18+6`

## Result

`taew2_1` is a viable opt-in presentation decoder for the accepted persistent
1.3B Strix path. It decoded the same 81-latent accepted stream into 81 finite
RGB frames with the expected streaming alignment, and a live 81-frame session
remained finite through the rolling KV window. The output is visibly somewhat
softer/different from the canonical Wan VAE, but the sampled lake/tree scene,
camera motion, and temporal progression remained coherent.

TAE is not a replacement for the canonical decoder for quality-sensitive
reference output. It is a presentation-only latency option.

## Latent contract

The accepted LingBot latent is model-space normalized Wan VAE `x0`, held by
the runner as `[C,T,H,W]` (`[16,21,48,84]` for the saved stream). The canonical
decoder converts it with the LingBot VAE scale/shift:

```text
z = x0 / vae.scale[1] + vae.scale[0]
```

The pinned TAE Wan 2.1 Diffusers wrapper uses identity latent mean/std. The
correct TAE input is therefore the same accepted `x0`, with only the required
layout conversion:

```text
[C,T,H,W] -> [N,T,C,H,W]
[16,21,48,84] -> [1,21,16,48,84]
```

No additional LingBot VAE mean/std conversion is applied before TAE. An
initial trial that incorrectly applied the canonical VAE transform produced
oversaturated output and was superseded; that failure is retained in the
chronological findings ledger.

## Offline contiguous-stream qualification

The input was a saved accepted 21-latent stream, so generation, DiT state,
camera actions, and video serialization were removed from the decoder
comparison. Both decoders started from session initialization and received
the same sequential latent stream. TAE produced one frame from the first
latent after startup trim and four frames from each of the remaining 20
latents, for exactly 81 frames.

| Measurement | Canonical FP16 Wan VAE | TAEHV FP16 |
|---|---:|---:|
| Decoder initialization | 270.0 ms | 758.1 ms |
| First latent decode | 1046.7 ms | 52.0 ms |
| Warm filled-latent decode | 639.0 ms | 16.7 ms all output |
| Warm first RGB from a filled latent | whole decode | 7.7–8.1 ms offline |
| Peak PyTorch allocation | 3.071 GB | reported in raw JSON |
| Output frames | 81 | 81 |
| Finite | yes | yes |

The warm TAE stream was approximately 8 ms to its first output frame and
14.6–16.7 ms to drain the remaining frames. These are decoder-only GPU
measurements and are not divided by four. The full raw record is
[`metrics.json`](../results/raw/taehv-offline-384x672-3step-81f/metrics.json)
and the matched videos are `canonical.mp4` and `taehv.mp4` in that directory.

Numerically, mean absolute frame difference was `0.0319` in `[0,1]`; maximum
absolute difference reached 1.0 at clipped extrema. Canonical and TAE frame
means, adjacent-frame deltas, and temporal trends were similar. Human review
of beginning, middle, direction-change, and late frames found the same broad
scene and motion, with TAE softer in fine detail and somewhat different in
texture/edges. This is a quality observation, not pixel equivalence.

## Live opt-in session

The runner now accepts `--display-decoder taehv` and keeps canonical decoding
available as the default. TAE mode does not execute canonical VAE decoding in
parallel. It presents the first TAE frame before the exact deferred clean-KV
commit, drains the remaining TAE frames, then permits the next action only
after the clean KV and all TAE output work have completed.

The live 81-frame run used the same accepted 3-step schedule, `seed=42`,
`384x672`, `18+6`, and the existing example prompt/image/actions. It completed
21 chunks with finite output and the final cache state was:

```text
global KV end:       21168 tokens
local KV end:        18144 tokens
local capacity:      18144 tokens
frames:              81
```

The long-session raw record is
[`metrics.json`](../results/raw/interactive-taehv-384x672-3step-deferred-81f-video/metrics.json),
with video at
[`interactive.mp4`](../results/raw/interactive-taehv-384x672-3step-deferred-81f-video/interactive.mp4).

### Filled-window latency

The first few chunks include startup and growing-context effects. The product
comparison below uses chunks 18–20, after the 18-frame world-memory window is
full.

| Metric | Canonical accepted path | TAE presentation path | Change |
|---|---:|---:|---:|
| 3-step DiT | about 1202 ms | 1208–1212 ms | measurement variation |
| VAE/presentation GPU work | about 634 ms | 36.9–37.6 ms all frames | -596 ms |
| First RGB presented | about 1841 ms | 1229–1232 ms | about -609 ms |
| Clean KV commit | about 391 ms after first RGB | 385–387 ms after first RGB | unchanged |
| Next action permitted | about 2232 ms | 1644–1648 ms | about -586 ms |

Steady TAE first-RGB GPU time was 19.7–20.1 ms and the remaining four-frame
drain was about 17.1–17.5 ms. The long run's first live TAE use was slower
(`126.5 ms`) due to one-time runtime/kernel warm-up; a separate short run
showed an even larger first-use warm-up (`389.4 ms`). Subsequent chunks were
stable at approximately 20 ms first RGB and 37 ms all output.

The root action summary is not used as the filled-window product metric: it
includes early chunks with shorter context. Its long-run median action was
`1334.5 ms`, while the final five actions averaged `1624.2 ms`.

## Memory and state

The live run reported a peak PyTorch allocation of
`30,049,277,440` bytes and peak reserved allocation of
`42,358,276,096` bytes. Peak process RSS was
`25,869,799,424` bytes. These values include the full LingBot pipeline and
loaded model, not just TAE. The post-session device allocation was
`18,975,921,664` bytes. The device properties reported
`total_memory=114688MB`, while host memory reported
`130459455488` bytes total; these are UMA accounting views, not a claim that
all of that memory is physically resident in GPU pages.

The decoder change does not touch the DiT latent, self-attention KV, prompt
cache, camera/Plücker conditioning, RNG progression, or accepted world state.
The live session verified finite output, monotonic global KV progression,
local-window rollover, and sink retention. Decoder selection is a fresh-session
choice; no canonical-to-TAE cache migration is implemented.

## Reproduction

Offline comparison:

```bash
ROOT_DIR=$PWD
UPSTREAM_DIR=$ROOT_DIR/.upstream/lingbot-world-v2
PYTHONPATH="$UPSTREAM_DIR:$ROOT_DIR/scripts:$ROOT_DIR/.upstream/taehv${PYTHONPATH:+:$PYTHONPATH}" \
  .venv/bin/python scripts/taehv_offline_compare.py \
  --latent-path results/raw/taehv-latent-capture-384x672-3step-81f/accepted_latents.pt \
  --output-dir results/raw/taehv-offline-384x672-3step-81f \
  --vae-path models/lingbot-world-v2-1.3b-causal-fast/Wan2.1_VAE.pth \
  --taehv-dir .upstream/taehv \
  --device cuda:0 --dtype fp16
```

Live opt-in display mode adds:

```text
--display-decoder taehv --taehv-dir .upstream/taehv
```

The exact long-run command and complete arguments are preserved in the
`arguments` object of the live `metrics.json`.

## Decision

Keep TAEHV as an explicit opt-in interactive presentation mode. It clears the
offline and live correctness gates and removes roughly 0.6 s from filled-window
first-visible latency and next-action readiness on this host. Keep canonical
FP16 VAE as the default/reference decoder until a broader visual/task-quality
evaluation establishes that TAE's softer detail is acceptable for the target
application.
