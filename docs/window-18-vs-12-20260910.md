# Persistent window A/B — 18 frames vs 12 frames (2026-09-10)

## Question

Does reducing the actual attended historical capacity from 18 frames to 12
frames recover useful interactive latency without damaging persistent causal
world behavior?

This was one bounded A/B. The sampler, geometry, renderer, sink size, queue
behavior, and execution order were unchanged. The accepted 18-frame default
was not changed.

## Configuration

```text
384×672 actual geometry
48×84 latent geometry
1008 tokens/frame
chunk_size=1
3 denoise: 999 → 899 → 702
exact deferred t=0 clean-KV commit
BF16 DiT, PyTorch fused SDPA
FP16 TAEHV taew2_1 presentation decoder
serial execution
sink_size=6
```

The same deterministic 40-action traversal was used for both runs:

```text
w,w,j,w,l,l,s,s,j,w,d,d,w,l,a,a,w,j,s,l,w,w,d,j,a,s,l,w,d,d,j,w,a,a,l,s,w,j,l,w
```

Authoritative timings came from unprofiled runs without video capture. Each
run included bootstrap plus 40 actions and completed 41 rows successfully.

```bash
ACTIONS='w,w,j,w,l,l,s,s,j,w,d,d,w,l,a,a,w,j,s,l,w,w,d,j,a,s,l,w,d,d,j,w,a,a,l,s,w,j,l,w'

LINGBOT_LIVE_OUTPUT_DIR=results/raw/live-window18-vs12-control-v2 \
LINGBOT_LIVE_MAX_ACTIONS=40 \
LINGBOT_LIVE_TIMEOUT_SECONDS=900 \
bash scripts/run_live.sh --scripted-actions "$ACTIONS"

LINGBOT_LIVE_OUTPUT_DIR=results/raw/live-window18-vs12-candidate \
LINGBOT_LIVE_MAX_ACTIONS=40 \
LINGBOT_LIVE_TIMEOUT_SECONDS=900 \
bash scripts/run_live.sh --local-attn-size 12 --scripted-actions "$ACTIONS"
```

The candidate's detailed SDPA check used profile contexts 11 and 12 only;
those intrusive timings are used to verify K reduction, not as product
latency measurements.

## Cache accounting

The control allocates 18 frames × 1008 tokens = 18,144 tokens. The candidate
allocates 12 frames × 1008 tokens = 12,096 tokens. In both cases the six sink
frames are inside the physical capacity; `18+6` does not mean 24 attended
frames.

| Configuration | Sink | Recent | Current | Total K | Global position at final row |
|---|---:|---:|---:|---:|---:|
| 18-frame control, rolled | 6,048 | 11,088 | 1,008 | 18,144 | 41,328 |
| 12-frame candidate, rolled | 6,048 | 5,040 | 1,008 | 12,096 | 41,328 |

Before the first eviction, the cache is contiguous and the sink policy is
logical rather than physically split. The 12-frame candidate reaches full
capacity at chunk 11. At chunk 12 it begins rolling; the runtime reports
`6,048 + 5,040 + 1,008 = 12,096` tokens and retains the configured sink.
Global position continues monotonically while local K remains bounded.

TAE first-RGB work remained approximately 20 ms in both paths. The primary
product result is therefore from shorter historical self-attention, not from
the presentation decoder.

The candidate's full-window first-visible improvement is approximately
197 ms and its rolled steady-state improvement is approximately 230 ms. Its
next-action-ready improvement is approximately 300 ms after rollover. This
exceeds the 150 ms experiment threshold.

Measured current allocations were approximately 19.10 GB allocated / 19.67 GB
reserved for the 18-frame run and 17.98 GB / 18.60 GB for the 12-frame run in
the steady region. RSS was approximately 3.57 GB in both process snapshots.
The reported PyTorch peak includes backend warm-up and was not used to claim a
per-action memory saving.

## Correctness and quality

Both unprofiled 40-action sessions were finite throughout. The final rows
reported:

```text
global position: 41,328 tokens
18-frame local K: 18,144 tokens
12-frame local K: 12,096 tokens
18-frame sink/recent/current: 6,048 / 11,088 / 1,008
12-frame sink/recent/current: 6,048 / 5,040 / 1,008
```

Both sessions included forward motion, turns, reversals, strafing, and
multiple local-window turnovers. Runtime checks showed monotonic global
progression, bounded local K, retained sink state, finite latents, and finite
decoded RGB. No frozen output, numerical collapse, or obvious chunk seam was
observed in the captured traversal.

The matched videos show the expected deterministic agreement through the
early portion, then diverge after the candidate forgets history that the
control still retains. Both remain recognizable, coherent lake/tree scenes
through the late samples. The 12-frame output has detectable scene/texture
variation relative to the control; this is the expected quality tradeoff, so
the result is classified **ACCEPT INTERACTIVE**, not bit-equivalent ACCEPT.

The scripted sequence visibly exercised action changes, but this run was not a
separate matched-state action-dependence timing test. No claim is made that
the two paths produce identical revisits; the longer visual result is the
reason to keep 18 frames available as the quality/reference mode.

## Decision

**ACCEPT INTERACTIVE.** The 12-frame candidate recovers roughly 0.23 seconds
of rolled first-visible latency and 0.30 seconds of rolled next-action
readiness while preserving finite, bounded, rolling causal state over the
40-action test. It has a detectable but not catastrophic persistent-world
quality tradeoff, so it should remain opt-in and should not replace the
18-frame default without a product decision.

Recommended use:

```bash
bash scripts/run_live.sh --local-attn-size 12
```

The next single experiment should be a fresh persistent A/B at
`local_attn_size=14`, `sink_size=6`, using the same traversal, to test whether
most of the latency recovery can be retained with less history loss. Do not
start that experiment from this commit without first reporting this result.
